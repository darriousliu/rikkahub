Cause:
  getOrPut installs a Pending entry, then runs its factory. The factory synchronously updates
  _sessionsVersion. Its eager StateFlow collector re-enters getConversationJobs on the same main
  thread and calls valuesSnapshot. valuesSnapshot encounters that same incomplete Pending and
  spins forever in await(), so the outer factory can never reach pending.complete().

Conclusion:
  Deterministic app-side same-thread re-entrancy deadlock expressed as a busy spin. This is not
  explained by emulator-wide CPU, I/O, memory, SurfaceFlinger, or system_server starvation.

Candidate fix location (not applied):
  ChatService.getOrCreateSession: publish _sessionsVersion only after getOrPut has returned and
  the map entry is Ready. A blocking implementation of Pending.await alone would still deadlock
  on this same-thread re-entry; it would only remove the CPU spin.
